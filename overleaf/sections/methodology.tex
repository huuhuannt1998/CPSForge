\section{Methodology}
\label{sec:methodology}

Our evaluation methodology measures attacker effectiveness, defense blocking rates, and the interaction between context, timing, model choice, and defense type in a closed-loop CPS setting.

\subsection{Experiment Workflow}
Each experiment proceeds as follows:
\begin{enumerate}[leftmargin=1.2em]
    \item Initialize the process in a known safe state via the scene reset procedure.
    \item Start the PLC--Factory~I/O control loop and the observation layer (500\,ms polling).
    \item For each polling step, record a structured plant snapshot.
    \item Every $k{=}3$ steps, invoke the attacker (random, static LLM, or online MITM).
    \item If the attacker decides ``attack,'' pass the proposed write through the defense chain: safety shield $\to$ PhaseAwareShield $\to$ IntentConsistencyChecker $\to$ LLM Defender.
    \item Execute approved writes on the live PLC; log blocked writes.
    \item Record per-step structured log (\texttt{UnifiedStepLog}, 33+ fields) to Parquet.
    \item Continue for 60~steps or until the wall-clock limit.
\end{enumerate}

\subsection{Attacker Variants}
We compare three attacker classes (RQ3):
\begin{itemize}[leftmargin=1.2em]
    \item \textbf{Random baseline:} bounded random perturbations over the configured attack surface. Always attacks (no wait decisions). Provides the lower bound on effectiveness.
    \item \textbf{Static LLM attacker:} receives full context once, proposes actions without observing process feedback. Tests LLM capability without online adaptation.
    \item \textbf{Online MITM attacker (C1):} operates within the PLC control loop with the observe--infer--decide--act cycle described in Section~\ref{sec:design:attacker}. Can exploit timing and phase transitions.
\end{itemize}

\subsection{Model Variants}
\textbf{Primary model (RQ1--RQ4):} Qwen2.5-3B-Instruct, a standard transformer architecture running in 4-bit NF4 quantization via bitsandbytes on an NVIDIA RTX~A4000 (16\,GB VRAM). Evaluated in both base and QLoRA-finetuned variants (RQ2).

\textbf{Cross-model comparison (RQ5):} Three models from two families, all in 4-bit NF4:
\begin{itemize}[leftmargin=1.2em,nosep]
    \item \textbf{Qwen2.5-3B-Instruct} (${\sim}$6\,GB): primary model (Qwen family).
    \item \textbf{Qwen3-1.7B} (${\sim}$4\,GB): within-family scaling comparator (smaller model).
    \item \textbf{SmolLM3-3B} (${\sim}$6\,GB): HuggingFace architecture (cross-family).
\end{itemize}

\textbf{Frontier model (RQ6):} GPT-4o-mini~\cite{openai2024gpt4omini}, accessed via the OpenAI API. This model extends the comparison beyond local 3B-class models to a frontier-tier API model with substantially larger parameter count and instruction-following capability. When used as defender, the local Qwen2.5-3B-Instruct model evaluates GPT-4o-mini proposals, preserving the symmetric LLM-vs-LLM defense design while testing cross-model defense generalization.

\subsection{Context Tiers}
Three strictly controlled context levels for ablation (RQ1):
\begin{itemize}[leftmargin=1.2em]
    \item \textbf{Minimal:} current sensor/actuator snapshot (values only), attacker goal, tag names. No descriptions, no ranges, no history.
    \item \textbf{Partial:} adds tag descriptions, value ranges, short history (5~steps), scene summary, and derived features (rates of change).
    \item \textbf{Full:} adds inferred process phase with confidence, prior action history with observed effects, scene-specific attack guidance, and safety rule summary.
\end{itemize}

Only \texttt{context\_level} varies between comparison cells; all other parameters (scene, duration, budget, polling rate, model) are held constant.

\subsection{Defender Variants}
We evaluate seven defense configurations (RQ4):
\begin{itemize}[leftmargin=1.2em]
    \item \textbf{None:} no defense (measures raw attacker capability).
    \item \textbf{Baseline:} threshold + invariant detectors (fixed-rule detectors calibrated per scene).
    \item \textbf{Phase-aware shield (C4):} blocks writes inconsistent with the inferred process phase.
    \item \textbf{Intent-consistency checker (C4):} blocks writes opposing the controller's current trend.
    \item \textbf{Combined:} phase-aware shield + intent-consistency checker together.
    \item \textbf{LLM defender (novel):} an LLM-based anomaly scorer that evaluates each proposed write using the same model and context infrastructure as the attacker (Section~\ref{sec:design:llm-defender}).
    \item \textbf{LLM combined:} phase-aware + intent-checker + LLM defender together.
\end{itemize}

The LLM defender creates a symmetric evaluation: the same model architecture serves as both attacker and defender. This tests whether an LLM can detect its own class of attacks, and whether combining LLM-based and rule-based defenses provides stronger protection than either alone.

\subsection{Metrics}
Let $N_{\text{sub}}$ be submitted LLM decisions, $N_{\text{schema}}$ schema-valid outputs, $N_{\text{exec}}$ executed attacks, and $N_{\text{succ}}$ successful attacks. The primary metrics reported in the evaluation tables are:
\begin{itemize}[leftmargin=1.2em]
    \item \textbf{Attack Success Rate (ASR):} $N_{\text{succ}} / N_{\text{exec}}$, computed post-hoc by comparing target tag value at step $N-1$ (before write) vs.\ $N+2$ (after). An attack succeeds if the tag moves toward the injected value.
    \item \textbf{Valid Action Rate (VAR):} $N_{\text{schema}} / N_{\text{sub}}$, measuring how often the LLM produces parseable, schema-compliant JSON output.
    \item \textbf{Prevention rate:} $N_{\text{blocked}} / N_{\text{attack\_proposals}}$, fraction of attack proposals blocked by the defense chain before PLC write. Includes safety shield blocks; ``None'' defense rows show safety-shield-only prevention.
    \item \textbf{LLM block rate:} number of proposals blocked by the LLM defender specifically, reported in the LLM column of Tables~\ref{tab:defense_comparison}--\ref{tab:defense_finetuned}.
    \item \textbf{LLM inference latency:} mean time from prompt submission to parsed response (ms), reported in Table~\ref{tab:context_ablation}.
\end{itemize}

For RQ1, we compute the \emph{context gain} $\Delta_{\text{ctx}} = \text{ASR}_{\text{full}} - \text{ASR}_{\text{minimal}}$ per scene. For RQ2, we compute $\Delta$ASR and $\Delta$VAR between finetuned and base variants. For RQ4, we compare prevention rates and ASR across all seven defense variants. Run-to-run variance is reported in Table~\ref{tab:variance}; all point estimates should be interpreted with the caveat that $n=3$ repeats yields wide confidence intervals for rare-event metrics.

\subsection{Scenes and Scale}

The evaluation covers three Factory~I/O scenes spanning continuous and discrete process types:
\begin{itemize}[leftmargin=1.2em,nosep]
    \item \textbf{Level Control} (15~tags): continuous PID tank fill/drain. Attacks cause overflow, underflow, or PID instability.
    \item \textbf{Sorting by Weight} (35~tags): discrete 3-way weight-based sorting. Attacks cause missorts (wrong routing via threshold shift), jams (wrong diverter activation), or stall (conveyor shutdown).
    \item \textbf{Sorting by Height} (30~tags): discrete 2-way height-based sorting. Attacks cause missorts (wrong transfer gate), jams, or stall.
\end{itemize}

These scenes cover an order-of-magnitude range in tag complexity (15--35~tags) and include both continuous control (PID) and discrete state-machine processes.

\subsection{Experiment Matrix}

The experiment matrix is organized into five research questions:
\begin{itemize}[leftmargin=1.2em]
    \item \textbf{RQ1 (Context):} $3$~contexts $\times$ $3$~scenes $\times$ $3$~repeats = 27~runs. Fix: online MITM red team, Qwen2.5-3B base, no blue team.
    \item \textbf{RQ2 (Fine-Tuning):} $2$~model variants (base, finetuned) $\times$ $2$~contexts $\times$ $3$~scenes $\times$ $3$~repeats = 36~runs. Fix: online MITM, no defense. The finetuned model serves both red and blue team roles.
    \item \textbf{RQ3 (Feedback Loop):} $3$~attacker types (random, static LLM, online MITM) $\times$ $3$~scenes $\times$ $3$~repeats = 27~runs. Fix: full context, base model, no defense.
    \item \textbf{RQ4 (Blue Team):} $2$~model variants $\times$ $7$~defense variants $\times$ $3$~scenes $\times$ $3$~repeats = 126~runs. Fix: online MITM red team, full context. The model variant controls both red and blue team symmetrically.
    \item \textbf{RQ5 (Cross-Model):} $3$~models $\times$ $2$~contexts $\times$ $2$~attackers $\times$ $2$~scenes $\times$ $3$~repeats = 72~runs. Fix: no defense.
    \item \textbf{RQ6 (Frontier Model):} $5$~conditions (3~context-only + 2~defense) $\times$ $3$~scenes $\times$ $3$~repeats = 45~runs. Fix: online MITM, GPT-4o-mini via OpenAI API. Defense cells use full context with LLM defender (local Qwen2.5-3B) evaluating GPT-4o-mini proposals.
\end{itemize}
Total: 333 experiment runs, all complete: 27~(RQ1) + 36~(RQ2) + 27~(RQ3) + 126~(RQ4) + 72~(RQ5) + 45~(RQ6). Each run executes 60~steps at 500\,ms polling, with attack budget of 10 and LLM decision calls every 3~steps.

\subsection{Ground Truth}
\label{sec:methodology:gt}
Ground-truth labeling is derived from the experiment protocol. Each polling step is labeled as \emph{attack-active} or \emph{normal} based on whether a shield-approved attack action was active during that step. This label is recorded in the trace metadata at runtime, not post hoc.

\subsection{Reproducibility}
\label{sec:methodology:reproducibility}
Every run produces a self-contained artifact folder containing: (i)~the full per-step trace in Parquet format (\texttt{UnifiedStepLog} with 33+ fields), (ii)~run metadata in JSON (scene, attacker, context, model, defense, attack counts), and (iii)~a checkpoint system for resumable experiment execution. PRNG seeds are recorded, context payloads are hashed, and all artifacts are saved for post-hoc analysis.
