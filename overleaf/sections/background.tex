\section{Background and Motivation}
\label{sec:background}

\subsection{Cyber-Physical Systems and Industrial Control}

Cyber-physical systems combine software control, networked communication, and physical dynamics. In industrial automation, PLCs serve as the primary control components that execute ladder logic or structured text, interact with sensors and actuators, and enforce operational sequences. The correctness of such systems depends not only on software behavior, but also on scan timing, process feedback, interlocks, and safety thresholds.

Compared to traditional IT environments, CPS attacks are constrained by the physical process. A successful adversary must reason about actuator timing, sensor semantics, controller state, and process dependencies. Similarly, effective defense must consider more than network traces or software logs; it must also account for physical behavior and unsafe state transitions.

\subsection{Why LLMs Matter in CPS Communication Security}

PLC communication streams carry structured, semantically rich data: tag names, values, types, and the temporal sequence of reads and writes. LLMs can reason over exactly this kind of structured telemetry --- inferring what the controller is trying to do, whether a proposed write is consistent with current process state, and which writes are most likely to cause physical impact. Recent work has shown that LLMs can generate process-aware attacks~\cite{ahmed2025attackllm}, synthesize invariants~\cite{fakih2024llm4plc}, and support security analysis~\cite{xu2024llm_cybersec_survey}. However, these studies operate offline on static traces, not on live communication streams.

The research question this paper addresses is whether an LLM embedded as a live man-in-the-middle agent in real PLC communication can perform effective attack and defense analysis --- and whether insights derived from that live stream differ from those available to offline analysis. We also ask: how much of the communication stream must the LLM observe (RQ1), does training on real communication traces improve both roles (RQ2), and does online stream feedback matter vs.\ a single snapshot (RQ3)?

\subsection{Limits of Existing Evaluation Practice}

Much of the current CPS security literature relies on benchmark datasets, offline detection experiments, or scripted attack scenarios. While these methods are useful, they do not fully capture the interaction between a live controller, evolving plant state, and actuation decisions. Offline traces cannot reproduce real controller scan cycles, online state transitions, or the consequences of repeated attack attempts.

Likewise, recent LLM-based CPS studies often stop at anomaly explanation, invariant extraction, or attack ideation. Without a closed-loop execution environment, it remains unclear whether LLM-generated strategies are actually process-valid, whether they survive practical constraints, and whether defenses improve meaningfully after exposure to such attacks.

\subsection{Motivation for a Live Communication Testbed}

CPSForge is motivated by the need for a realistic yet safe platform for studying LLM analysis of live PLC communication. The real Siemens S7-1200 PLC provides authentic S7 protocol communication, real controller scan cycles, and actual tag behavior --- the exact communication stream an attacker or defender would see. Factory~I/O supplies reproducible software-emulated process scenes that respond to PLC writes with physically plausible state transitions, keeping the physical process safely virtualized while preserving realistic communication dynamics.

This combination --- which we term \emph{PLC-in-the-loop} --- means that every tag value the LLM observes is a real S7 protocol read from a live PLC, and every write the LLM proposes is a real S7 write that changes the controller's data block. Unlike offline evaluations that replay static traces, CPSForge operates on the actual communication stream at runtime. The LLM sees what a real adversary or defender on the network would see: live tag values updating every 500\,ms, with real controller dynamics and timing.

The closed-loop design is also essential for the attacker comparison (RQ3). A one-shot attacker that receives a single snapshot of the communication stream cannot observe how the process responds to its actions, cannot time attacks to phase transitions, and cannot adapt when a proposed write is blocked. The online MITM attacker observes the stream continuously and can exploit exactly these dynamics. Whether this live feedback is necessary --- vs.\ a single snapshot --- is the empirical question RQ3 answers.

\subsection{Design Goals}

The design of CPSForge is guided by four main goals:

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Realism.} The system should operate over a real PLC and a live process emulator rather than relying solely on offline traces or purely synthetic controllers.
    \item \textbf{Safety.} No model or attack component should write directly to the controller without mediation by a safety layer.
    \item \textbf{Reproducibility.} Every experiment should produce structured artifacts that support replay, auditing, and analysis.
    \item \textbf{Adaptation.} The framework should support repeated attack and defense rounds so that defender improvement can be measured over time.
\end{itemize}

\subsection{Real-World CPS Attacks: Precedents and Patterns}
\label{sec:background:incidents}

Table~\ref{tab:incidents} summarizes the major publicly documented cyberattacks on industrial control systems. These incidents span two decades, multiple sectors, and a progression from manual single-point interventions to autonomous, protocol-aware, multi-stage campaigns. Three patterns are particularly relevant to CPSForge's design.

\textbf{Pattern 1: Data-plane manipulation suffices.} Stuxnet modified PLC data block DB890 to alter centrifuge speeds rather than replacing the entire PLC program~\cite{langner2013kill}. Industroyer issued standard IEC~60870-5-104 commands to open circuit breakers~\cite{cherepanov2017industroyer}. The Oldsmar attacker changed a single setpoint (NaOH concentration from 100\,ppm to 11,100\,ppm) via a TeamViewer session~\cite{cisa2021oldsmar}. In each case, the attacker operated \emph{within the existing communication protocol}, manipulating process data rather than deploying novel exploits. CPSForge's Tier~1 attacker directly models this pattern, injecting writes to PLC tags via standard S7 protocol.

\textbf{Pattern 2: Internal state persistence creates outsized impact.} Stuxnet's most damaging payload targeted frequency-converter drive parameters stored in PLC data blocks that the control logic trusted implicitly and never re-initialized~\cite{falliere2011w32}. The Maroochy Shire attacker exploited the SCADA system's trust in radio commands to repeatedly open sewage release valves over a three-month period~\cite{abrams2008maroochy}. CPSForge's Tier~2 (Deep State) attacker mirrors this: by writing to internal variables (\texttt{Enable}, \texttt{iState}, threshold registers) that the PLC reads but never refreshes, a single write persists indefinitely.

\textbf{Pattern 3: Attack sophistication is escalating toward automation.} From Maroochy Shire (manual valve commands, 2000) through BlackEnergy (scripted SCADA access, 2015) to PIPEDREAM/INCONTROLLER (modular OT-specific toolkit targeting Schneider and OMRON PLCs, 2022)~\cite{cisa2022pipedream}, the trend is toward reusable, protocol-aware attack frameworks that abstract away device-specific details. PIPEDREAM's virtual console even provides a command interface mirroring the target PLC's interface, enabling lower-skilled operators to execute sophisticated attacks~\cite{greenberg2022pipedream}. CPSForge's LLM-based attacker represents the logical next step in this trajectory: a \emph{general-purpose reasoning agent} that can interpret arbitrary process telemetry and decide when and how to intervene, without requiring pre-programmed attack scripts.
