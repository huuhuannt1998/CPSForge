\section{System Design}
\label{sec:design}

CPSForge is a closed-loop LLM red team / blue team framework for CPS security analysis. The architecture comprises five interacting layers---physical execution, observation, red team (attack generation), safety enforcement, and blue team (defense)---connected to a real PLC. The same LLM serves both red and blue team roles with different prompts, enabling symmetric analysis. The framework is configuration-driven: any CPS connected to a supported PLC can be analyzed by providing a scene YAML configuration. Figure~\ref{fig:architecture} illustrates the pipeline.

\subsection{Physical Execution Layer}

At the foundation of CPSForge is a PLC-in-the-loop execution environment. A Siemens S7-1200 PLC executes control logic deployed from TIA Portal~v17, while Factory~I/O serves as a software-based process emulator providing realistic plant dynamics. Communication uses python-snap7 over Ethernet at a 500\,ms polling interval.

Each process scene is represented as a scene profile containing tag metadata (addresses, types, ranges, descriptions), process descriptions, attack surface definitions, safety rules, and reset procedures. Three evaluation scenes cover both continuous and discrete process types:
\begin{itemize}[leftmargin=1.2em,nosep]
    \item \textbf{Level Control} (Scene~12, DB14, 15~tags): continuous PID tank fill/drain.
    \item \textbf{Sorting by Weight} (Scene~20, DB22, 35~tags): discrete 3-way weight classification.
    \item \textbf{Sorting by Height} (Scene~19, DB21, 30~tags): discrete 2-way height classification.
\end{itemize}

\subsection{Observation and Context Layer}

A middleware bridge continuously reads PLC state and records structured plant snapshots. Each snapshot includes sensor values, actuator states, controller mode bits, alarms, setpoints, and derived features (rates of change, moving averages). A sliding-window history buffer maintains the last 200~snapshots.

A rule-based phase inference engine determines the current operational phase (idle, filling, draining, sorting, alarm, etc.) from snapshot patterns. This phase information is consumed by both the attacker (for timing attacks to phase transitions) and the defenses (for blocking phase-inconsistent writes).

A modular context builder assembles three strictly controlled context tiers (minimal, partial, full) from the observation layer. The same context builder serves both red and blue team LLMs, ensuring a fair information basis for ablation studies.

\subsection{LLM Attacker Layer}
\label{sec:design:attacker}

The attack layer implements three attacker variants for controlled comparison (RQ3):

\paragraph{Random Baseline.} Bounded random perturbations over the scene's attack surface, with values drawn within configured tag ranges. Provides the lower bound on attack effectiveness.

\paragraph{Static LLM Attacker.} Receives scene context and a single plant snapshot, proposes attack actions through a one-shot pipeline without observing process feedback. Tests LLM attack capability without online adaptation.

\paragraph{Online MITM Attacker (C1).} The core contribution. Operates within the PLC control loop as a man-in-the-middle adversary. Every $k{=}3$ polling cycles:
\begin{enumerate}[leftmargin=2em,nosep]
    \item Observe current PLC state (sensors, actuators, setpoints).
    \item Inspect short history from sliding window buffer.
    \item Infer current operational phase via rule-based phase engine.
    \item Assemble context-tier-specific prompt (minimal, partial, or full).
    \item LLM decides: \textbf{attack} or \textbf{wait}.
    \item If attack: emit structured \texttt{AttackDecision} JSON with target tag, value, duration, and reasoning.
    \item Pass through the full defense chain before PLC execution.
    \item Observe result; continue iteratively.
\end{enumerate}

All LLM outputs are parsed into a strict JSON schema (\texttt{AttackDecision}). Invalid outputs default to ``wait'' (safe fallback). Attack budget: max 10 per run.

\paragraph{Deep State MITM Attacker (Tier~2).} Extends the online MITM to target \emph{internal PLC state variables} that the control logic reads but never overwrites---setpoints, classification thresholds, enable flags, and state-machine registers. Because these variables are not refreshed by the PLC scan cycle, a single S7 write persists indefinitely (the ``Stuxnet DB890 pattern,'' see Section~\ref{sec:threat}). The attacker prompt uses the scene's \texttt{deep\_state\_attack\_surface} configuration (specifying persistence, attack category, and state-machine effect for each target) instead of the I/O attack surface.  Eight attack categories are supported: threshold manipulation, state-machine jump, timer acceleration, safety kill-switch, decision-flag spoofing, setpoint hijack, counter spoofing, and mode manipulation.

\paragraph{Logic Analyzer (Tier~3).} An offline LLM-based code analysis tool that reads the original SCL source code for each scene's PLC program, identifies exploitable code-level vulnerabilities, and generates minimal adversarial SCL modifications.  Seven code modification categories are supported: dead-code injection, comparison inversion, timer alteration, interlock removal, gradual drift, state shortcut, and sensor clamping.  Deployment requires manual TIA Portal import---mirroring Stuxnet's offline payload development methodology.  Live validation on all three evaluation scenes confirmed that comparison-inversion modifications compile without errors and cause measurable physical disruption when downloaded to the PLC (see Section~\ref{sec:discussion:tiers}).

\subsection{Safety Shield}

The safety shield is the mandatory first gate before any write reaches the PLC. It evaluates seven sequential checks (see Section~\ref{sec:impl:shield-impl} for full details); the principal ones are:
\begin{enumerate}[leftmargin=2em,nosep]
    \item \textbf{Whitelist:} target tag must be in the scene's declared attack surface.
    \item \textbf{Range:} proposed value must lie within configured min/max bounds.
    \item \textbf{Duration cap:} attack duration must not exceed scene maximum.
    \item \textbf{Mutual exclusion:} conflicting actuators cannot be simultaneously active (e.g., \texttt{send\_left} and \texttt{send\_right} in sorting scenes).
    \item \textbf{Invariant:} hard physical-boundary rules specific to each scene.
\end{enumerate}

\noindent Additional checks (cooldown windows, interlocks, mode gates) are described in Section~\ref{sec:impl:shield-impl}. The shield runs in microseconds and is always active regardless of the defense variant.

\subsection{Defense Layer}
\label{sec:design:defense}

CPSForge evaluates seven defense configurations (RQ4), organized into three categories:

\subsubsection{Baseline Detectors}
Six traditional anomaly detectors run in parallel during execution: ThresholdDetector (per-tag rule-based), InvariantDetector (boolean process invariants), IsolationForest (point-wise anomaly scoring), OCSVM (kernel-boundary anomaly), CUSUM (cumulative-sum change-point detection), and LSTM-AE (sequence autoencoder reconstruction error).

\subsubsection{Novel Rule-Based Defenses (C4)}
Two novel defenses designed specifically for the LLM attacker threat model:

\paragraph{PhaseAwareShield.} Blocks PLC writes that are semantically inconsistent with the current operational phase. Standard range-check rules cannot block attacks where proposed values are individually legal but contextually wrong (e.g., opening the discharge valve during a fill phase). The PhaseAwareShield adds a phase-level reasoning layer using scene-specific rules that map process phases to blocked write patterns.

\paragraph{IntentConsistencyChecker.} Detects writes that oppose the controller's current trend. If the PID is actively reducing the fill valve, an attacker write that forces it open is flagged as intent-inconsistent and blocked.

\paragraph{StateConsistencyChecker (Tier~2 Defense).} Blocks writes that would cause illegal state transitions, timer anomalies, or unauthorized changes to protected internal variables.  Uses per-scene rule sets encoding: (i)~valid state-machine transitions (e.g., Sorting by Weight's 8-state machine permits only $\{0{\to}1, 1{\to}2, 1{\to}4, 1{\to}6, \ldots\}$); (ii)~timer jump limits (maximum single-step increment); (iii)~protected variables that are never writable (e.g., \texttt{Enable}, classification thresholds); and (iv)~classification guards that lock measurement values after the sensing phase.  Designed specifically to counter Tier~2 deep-state attacks.

\subsubsection{LLM Defender (Novel)}
\label{sec:design:llm-defender}

To create a symmetric evaluation---LLM attacker vs.\ LLM defender---we introduce an \textbf{LLM-based anomaly defender} that uses the same model architecture, context builder, and inference pipeline as the attacker, but with a defense-oriented prompt.

The LLM defender receives:
\begin{enumerate}[leftmargin=2em,nosep]
    \item Current process state (same observation as the attacker).
    \item The proposed PLC write (target tag, value, duration, action type).
    \item Scene description and control objective.
    \item Inferred process phase and recent history.
\end{enumerate}

It outputs a structured JSON decision:
\begin{itemize}[leftmargin=1.2em,nosep]
    \item \texttt{decision}: ``allow'' or ``block''
    \item \texttt{suspicion\_score}: 0.0 (clearly legitimate) to 1.0 (clearly malicious)
    \item \texttt{reasoning}: brief explanation
\end{itemize}

Writes with suspicion score $\geq 0.5$ or explicit ``block'' decisions are rejected. On LLM parse failure, the defender defaults to ``allow'' to avoid blocking legitimate controller writes.

This design enables several key comparisons:
\begin{itemize}[leftmargin=1.2em,nosep]
    \item \textbf{LLM vs.\ LLM:} Can a defender LLM detect attacks from an attacker LLM using the same model?
    \item \textbf{Rule-based vs.\ LLM defense:} Does the LLM defender outperform hand-crafted phase-aware rules?
    \item \textbf{Combined defense:} Does adding the LLM defender to rule-based defenses improve overall blocking rate?
\end{itemize}

\subsubsection{Defense Chain}
The full defense chain for a proposed write is:
\[
\text{Shield} \to \text{PhaseAware} \to \text{IntentChecker} \to \text{StateConsistency} \to \text{LLMDefender} \to \text{Execute}
\]
Each stage can independently block the write. A write must pass all active stages to reach the PLC. Tier~1 experiments use the first four stages; Tier~2 experiments activate the StateConsistencyChecker.

\subsection{Design Principles}

The system design follows four principles:
\begin{itemize}[leftmargin=1.5em]
    \item \textbf{No unrestricted direct actuation from any LLM.} All writes---both offensive and defensive---are mediated by the safety shield.
    \item \textbf{Symmetric red/blue team.} The red and blue team LLMs share the same model architecture, context pipeline, and inference infrastructure, enabling systematic analysis of any connected CPS.
    \item \textbf{All experiments are bounded by explicit safety rules} and produce replayable, auditable artifacts.
    \item \textbf{Structured outputs only.} Both red and blue team LLMs produce strict JSON schemas. No free-form text is executed.
\end{itemize}
