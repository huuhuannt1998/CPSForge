\section{Discussion}
\label{sec:discussion}

\subsection{CPSForge as a General-Purpose Framework}

A central design goal of CPSForge is generality: the framework is not tied to the specific Factory~I/O scenes used in this evaluation. The scene abstraction, context builder, defense chain, and experiment runner are all configuration-driven. To analyze a new CPS---e.g., a water treatment plant, power grid substation, or different manufacturing line---a user provides a YAML scene configuration specifying tags, types, addresses, attack surfaces, and safety rules. The LLM red and blue team agents, defense chain, and logging infrastructure require no code changes.

We use a real Siemens S7 PLC rather than a purely synthetic controller. Real controller scan timing, actual tag behavior, and live S7 protocol communication provide a faithful substrate for closed-loop red/blue team analysis. Factory~I/O is a software process emulator, not a physical plant (Section~\ref{sec:background}), but the framework supports any plant connected to the PLC. Prior PLC-based testbeds~\cite{dehlaghi2023icssim, garcia2025sphere, pramadi2026simpleics} establish this principle; CPSForge extends it to LLM-driven automated security analysis.

\subsection{Why the LLM Is Constrained}

CPSForge intentionally constrains LLM actions through structured schemas and a mandatory safety shield. This is both a safety decision and a research decision. From a safety perspective, unrestricted direct actuation is inappropriate in a live CPS setting~\cite{lanotte2022runtime_ics, baird2024scalable_enforcement}. From a research perspective, structured mediation makes it possible to evaluate red/blue team reasoning quality without conflating model output quality with uncontrolled execution privilege. The constraints also make the framework safe to deploy on production-adjacent hardware---a prerequisite for adoption as a practical security analysis tool.

\subsection{Symmetric Red/Blue Team and Multi-Model Rationale}

A key limitation of prior CPS-LLM evaluations is reliance on a single model~\cite{ahmed2025attackllm}. Our evaluation addresses this through four axes: (i)~\emph{within-family scaling} (RQ5): Qwen2.5-3B-Instruct (${\sim}$3B) vs.\ Qwen3-1.7B (${\sim}$1.7B), testing whether scale predicts red team quality; (ii)~\emph{cross-family} (RQ5): Qwen2.5-3B vs.\ SmolLM3-3B, testing whether capability is architecture-specific; (iii)~\emph{before/after fine-tuning} (RQ2): base vs.\ QLoRA-finetuned Qwen2.5-3B, testing whether task-specific training improves both red and blue team roles; and (iv)~\emph{frontier model scaling} (RQ6): local 3B-class vs.\ GPT-4o-mini API, testing whether a frontier model exhibits qualitatively different attack behavior. The fine-tuning uses dual-role training data (attack traces + defense decisions) so the same adapter serves both roles.

Critically, the LLM blue team uses the same model and context pipeline as the red team, enabling symmetric analysis. Our results show that this approach outperforms all rule-based defenses on Sorting by Height (100\% prevention rate vs.\ 0\% for rule-based).

\subsection{Key Findings}

The evaluation produces several notable findings across 333 experiment runs on three Factory~I/O scenes.

\textbf{Online feedback substantially outperforms one-shot designs.} The static one-shot LLM generates zero valid attack proposals across all scenes (Table~\ref{tab:attacker_comparison}). This reflects two factors: the 350-token output budget is insufficient for a multi-object JSON array, and without iterative process feedback the model produces low-confidence outputs that fail schema validation. Whether this gap is bridgeable with larger output budgets or chain-of-thought prompting is an open question; we report it as a lower bound. The online MITM attacker achieves up to 54\% ASR by observing live plant state, inferring process phase, and timing its actions---capabilities unavailable to a one-shot design.

\textbf{The LLM defender is the strongest defense.} On Sorting by Height, the LLM defender blocks 100\% of attack proposals (Table~\ref{tab:defense_comparison})---the only defense variant to achieve complete prevention. Baseline, intent, and combined rule-based defenses let all writes through, with ASR up to 16.7\%. This validates the symmetric LLM-vs-LLM defense design: the same model that reasons about attacks can effectively detect them.

\textbf{Full context causes self-deterrence on continuous-control scenes---but only for small models.} Full context produces zero attack proposals on Sorting by Weight and sharply suppresses proposals on Level Control (5 proposals, all shield-blocked, vs.\ 23 at minimal context) for the 3B-class Qwen2.5-3B model. However, GPT-4o-mini (RQ6) generates the maximum 30~proposals under full context on \emph{every} scene, including Sort.~Weight where Qwen completely self-deterres. Self-deterrence is therefore a \emph{model-capacity artifact}: continuous PID scenes expose safety rules and setpoint bounds that suppress the 3B model's confidence, but a frontier model ignores these cues and attacks regardless. On Sort.~Weight, the net effect under full context is the same (0\% ASR) but through different mechanisms: GPT-4o-mini's proposals are all shield-blocked (targets \texttt{heavy\_thresh} with out-of-range values), while Qwen generates zero proposals. The practical implication is that ``deterrence through transparency''---exposing operational context as a defense mechanism---is unreliable against frontier models. Fine-tuning (RQ2) can also break this pattern: the finetuned model achieves 36.7\% ASR on Level Control minimal where the base achieves 0\%.

\textbf{Attack capability scales with model size---but not linearly.} Qwen2.5-3B (13.7\% ASR) and SmolLM3-3B (11.7\%) achieve comparable results on Level Control, while Qwen3-1.7B achieves 0\% (Table~\ref{tab:crossmodel}). GPT-4o-mini (RQ6) achieves the highest ASR in the full evaluation: 100\% on Sort.~Weight minimal (18/18 writes), 66.7\% on Sort.~Weight partial, and 20\% on Level Control full---the only model to achieve nonzero ASR on Level Control under full context. However, on Sort.~Height, the frontier model achieves 0\% ASR despite executing all 30~writes in every cell---its target selection (actuator overrides on \texttt{enable}, \texttt{conveyor\_entry}) produces no observable physical effect. The relationship between model scale and attack effectiveness is therefore scene-dependent: larger models are strictly more aggressive (more proposals, no self-deterrence) but not universally more effective.

\textbf{Safety shield mediates all writes.} The mandatory safety shield mediates every write across all 333 runs. Out-of-range values proposed by the LLM are blocked before reaching the PLC. The shield's per-step overhead is negligible relative to the 500\,ms polling interval.

\subsection{Limitations}

The current evaluation has several limitations.

\textbf{Model capacity for CPS reasoning.} Our evaluation spans from 1.7B-class local models to a frontier API model (GPT-4o-mini). The primary model (Qwen2.5-3B-Instruct) and GPT-4o-mini both achieve reliable JSON schema compliance with the structured output format. RQ6 demonstrates that model scale has a significant effect on self-deterrence (eliminated at frontier scale) and ASR (up to 100\% on Sort.~Weight). Whether mid-range models (7B--13B) exhibit intermediate behavior remains an open question.

\textbf{LLM attacker effectiveness relative to baselines.} On Sorting by Weight, the online MITM dominates: 53.8\% ASR vs.\ 0\% for random (Table~\ref{tab:attacker_comparison}). On Level Control, the online MITM generates 14 proposals but all are shield-blocked (0~writes executed), while random achieves 10.0\% ASR with 10~writes---the MITM proposes out-of-range values under full context, whereas random draws within configured bounds. Under partial context (Table~\ref{tab:context_ablation}), MITM writes do execute but the PID controller corrects them within the polling window. On Sorting by Height, random achieves 13.3\% vs.\ MITM's 3.3\%, but the difference is \emph{not statistically significant}: Wilson 95\% CIs overlap ($[5\%, 30\%]$ vs.\ $[1\%, 17\%]$, $n=30$ each). We do not claim that random outperforms MITM on this scene; the observed difference is consistent with sampling variance.

\textbf{Sorting by Weight prompt complexity.} The 35-tag Sorting by Weight scene generates large prompts (${\sim}$2{,}000 tokens for full context) that challenge 3B-class models. All three cross-model variants generate zero proposals on this scene, and LLM inference latency reaches ${\sim}$33\,s per call. This suggests a practical limit on scene complexity for small local models.

\textbf{Attacker behavior under defense.} Several defense variants see zero attack proposals from the LLM attacker (Table~\ref{tab:defense_comparison}). The attacker's context includes observations that may implicitly signal the presence of defenses, causing ``wait'' decisions. While this is itself a defense effect (deterrence), it limits our ability to measure per-defense blocking rates on scenes where the attacker self-suppresses.

\textbf{Defense novelty and scope.} The PhaseAwareShield and IntentConsistencyChecker are rule-based defenses that encode domain knowledge (process phases, controller trends) into blocking rules. Individually, they are straightforward engineering contributions. Their novelty lies in the combination with the LLM defender and the systematic comparison across seven defense variants on a live PLC---a comparison absent from prior work. The LLM defender's 100\% blocking rate on Sorting by Height, where all rule-based defenses fail, demonstrates that process-context-aware LLM reasoning provides a qualitatively different defense capability.

\textbf{Threat model practicality.} Attacks are bounded by the configured attack surface, duration caps, and a budget of 10 attacks per 30-second run. A real attacker with process-level network access would not face these constraints. Our experimental envelope is designed for safe, controlled measurement rather than maximum adversarial impact. The results provide a lower bound on attack capability---the safety constraints mean that any observed attacks represent attacks that would also succeed without constraints, while the converse is not guaranteed.

\textbf{Scene scale and representativeness.} The evaluated scenes range from 15 to 35~tags across three scenes, which is smaller in scale than full-scale ICS testbeds such as SWaT (51~sensors/actuators across 6~linked process stages)~\cite{mathur2016swat}. The Factory~I/O scenes cover both continuous (PID) and discrete (state-machine) control paradigms but lack two properties of production environments: (i)~\emph{cross-subsystem dependencies}---SWaT's six stages are serially connected, so an attack on stage~1 can cascade to stages~2--6, while our three scenes are independent single-stage processes; and (ii)~\emph{concurrent multi-loop control}---production plants run dozens of interlocked PID loops simultaneously, while Level Control runs a single PID.

The scene YAML abstraction does generalize to higher-complexity plants: connecting a new plant requires specifying tags, types, addresses, attack surfaces, and safety rules---no framework code changes. However, we have not \emph{validated} this generalization empirically. Specifically, two open questions remain: (a)~whether the 3B-class LLM can reason effectively about 50+ tag scenes (our Sorting by Weight results at 35~tags already show degraded performance with 0\% cross-model ASR), and (b)~whether cascade effects across linked subsystems require multi-step attack planning capabilities beyond the current single-write-per-decision design.

\textbf{Cross-model scope.} The evaluation compares three local models ($\leq$3B parameters in 4-bit) from two families plus one frontier API model (GPT-4o-mini). RQ6 demonstrates that model-scale effects are significant: self-deterrence vanishes, ASR increases substantially on some scenes, and the relationship between context and effectiveness reverses. Comparison with additional frontier models (GPT-4, Claude) and mid-range open models (7B--13B) would further characterize the capability--scale relationship.

\textbf{LLM defender false-positive rate (critical limitation).} The LLM defender's 100\% blocking rate on Sorting by Height is the strongest result in this paper, but it \emph{must} be qualified. We conducted a controlled FPR study on Level Control using a \emph{probe attacker} that generates known-legitimate writes---small perturbations ($\pm 0.3$) around current controller values for setpoint, fill valve, discharge valve, and enable---and routes them through the full defense chain. In 60-step runs (20~probes each) across four conditions (2~models $\times$ 2~defense variants), the results are unambiguous:

\begin{itemize}[nosep]
    \item Base model + LLM defender: 20/20 blocked (FPR\,=\,100\%, scores\,=\,0.80)
    \item Base model + LLM combined: 20/20 blocked (FPR\,=\,100\%; 2~by PhaseAwareShield, 18~by LLM)
    \item Fine-tuned + LLM defender: 20/20 blocked (FPR\,=\,100\%, scores\,=\,0.90--0.95)
    \item Fine-tuned + LLM combined: 19/20 blocked (FPR\,=\,95\%; 19~by LLM, 1~allowed)
\end{itemize}

\noindent Aggregating Level Control: 79 of 80 legitimate probes were blocked (FPR\,=\,98.75\%, 95\% Wilson CI [93.3\%, 99.8\%]). We extended this study to all three scenes using the same probe-attacker methodology (2~models $\times$ 2~defense variants $\times$ 3~repeats per scene). Sorting by Weight: 72/72 blocked (FPR\,=\,100\%). Sorting by Height: 71/71 blocked (FPR\,=\,100\%). \textbf{Cross-scene aggregate: 226 of 229 legitimate probes blocked (FPR\,=\,98.7\%, 95\% Wilson CI [96.2\%, 99.6\%]).} The result is scene-independent: \textbf{the LLM defender operates as a ``block-everything'' policy rather than a discriminating anomaly detector.} Fine-tuning on attack+defense traces (including 1366 ``allow'' examples) did not improve discrimination---it \emph{increased} blocking confidence (0.90--0.95 vs.\ 0.80 base), reinforcing the block-all pattern.

This finding has three implications. First, the 100\% attack-blocking rate on Sorting by Height is trivially achievable by any policy that rejects all writes; the LLM's contribution is not selective detection but blanket rejection. The cross-scene results (100\% FPR on both discrete scenes, 96.5\% on the continuous PID scene) confirm this is not scene-specific. Second, the current prompt and context pipeline do not provide sufficient information for the 3B-class model to distinguish between a legitimate controller write and a small adversarial perturbation of the same tag. Third, the defense fine-tuning data (608~block, 1366~allow) failed to teach allow/block discrimination, likely because the ``allow'' examples also present writes during normal operation---the same context the model sees in the FPR probes---but with no distinguishing feature beyond the label.

\subsubsection{FPR Measurement Protocol}
\label{sec:fpr_protocol}

The FPR study uses a probe-attacker methodology. (1)~Run the scene for 20~steps under normal PLC operation with a probe attacker that generates legitimate-range writes ($\pm 0.3$ perturbation) every 3~steps ($\sim$6~probes/run). (2)~Each probe is routed through the full defense chain (safety shield $\to$ PhaseAwareShield $\to$ IntentConsistencyChecker $\to$ LLM defender) using the same context pipeline as attack experiments. (3)~Compute FPR\,=\,$N_{\text{blocked}} / N_{\text{probes}}$. (4)~We report results across all three scenes (2~models $\times$ 2~defense variants $\times$ 3~repeats per scene, 229~total probes). For ICS runtime monitoring, FPR\,$<$\,1\% is a common target~\cite{moriano2025adaptive_anomaly}; the observed 95--100\% FPR across all three scenes exceeds this by two orders of magnitude, confirming that the LLM defender in its current form is not deployment-ready.

\textbf{Statistical power.} The experiment matrix uses 3~repeats per cell (333 total runs). Confidence intervals for individual cells may still be wide for rare-event metrics such as ASR on resilient scenes (Table~\ref{tab:variance}).

\textbf{Single PLC and plant.} All experiments use one Siemens S7-1200 PLC with Factory~I/O. While the scene abstraction supports diverse plant configurations, generalizability to other PLC families or real physical plants remains to be validated. Planned extensions include: (i)~Allen-Bradley CompactLogix via pylogix (EtherNet/IP protocol), which would test whether the tag-level attack abstraction transfers across PLC families; (ii)~Schneider Modicon via pymodbus, testing Modbus/TCP as an alternative field protocol; and (iii)~a multi-PLC cascaded Factory~I/O setup (e.g., linking Sorting by Weight output to a downstream packaging scene) to study cross-subsystem attack propagation. Physical testbed validation---connecting CPSForge to a real water treatment or power grid pilot plant---is the ultimate generalizability test but requires institutional testbed access.

\textbf{ML detector portability.} Trained ML detectors (OCSVM, Isolation Forest, LSTM-AD) are sensitive to the feature dimensionality of the scene on which they were trained. When evaluated on traces from a different scene configuration with a mismatched tag count, pre-trained models fail. This motivates per-scene model management and automated retraining when scene configurations change.

\textbf{Ground-truth labeling.} As discussed in Section~\ref{sec:methodology:gt}, protocol-based attack labels do not perfectly correspond to physical-process anomalies. Steps where the injected value causes no observable deviation are still labeled ``attack-active,'' and residual effects after an attack ends are labeled ``normal.'' This means the reported F1 values are approximate and would differ under a physics-based labeling scheme. Developing dual-label ground truth---protocol-level and physics-level---is an important direction for future work.

\subsection{Comparison to Most Related Work}

\textbf{Why direct reimplementation comparison is infeasible.} The most directly comparable prior systems---AttackLLM~\cite{ahmed2025attackllm}, MALF~\cite{ning2025malf}, and HARVEY~\cite{garcia2017harvey}---cannot be directly reimplemented on our testbed for three reasons. First, \emph{testbed incompatibility}: AttackLLM is designed for the SWaT water-treatment testbed (51 sensors/actuators, ABB AC500 PLCs, Modbus/TCP); our S7-1200 + Factory~I/O setup uses a different PLC family, protocol (S7), and scene scale (15--35 tags). Porting AttackLLM would require rewriting its entire prompt suite and evaluation pipeline for S7 tag semantics. Second, \emph{abstraction-level mismatch}: MALF operates at the network-packet level (Modbus/S7Comm frame fuzzing), while CPSForge operates at the process-tag level. These are fundamentally different attack surfaces---packet-level fuzzing tests protocol parsers, while tag-level manipulation tests process logic. A fair comparison would require implementing both abstraction levels for the same plant, which neither framework supports. Third, \emph{model access}: AttackLLM uses GPT-4 via API, while CPSForge uses local 3B-class models. ASR differences would conflate model capability with framework design.

\textbf{Partial comparison via static LLM baseline.} Our static LLM attacker (Table~\ref{tab:attacker_comparison}) serves as a structural proxy for the AttackLLM design philosophy: both use a single LLM invocation with full context to generate attack proposals without observing process feedback. The static LLM achieves 0\% VAR (no schema-valid outputs) across all scenes, attributable to the 350-token output budget and the absence of iterative refinement. AttackLLM uses GPT-4 (with far larger context and output windows) and a human-in-the-loop validation step, which would likely overcome the token-budget limitation. The comparison is therefore not between frameworks but between \emph{attack paradigms}: one-shot batch generation (AttackLLM, static LLM) versus online closed-loop adaptation (CPSForge online MITM). The online MITM's 3--54\% ASR across scenes demonstrates that iterative process feedback provides a capability that one-shot designs lack, regardless of model scale.

Compared to Evo-Defender~\cite{hu2025evodefender}, CPSForge uses LLM reasoning rather than fuzzing for attack generation and runs on a real PLC rather than a simulator. Compared to PentestGPT~\cite{deng2024pentestgpt} and Hackphyr~\cite{rigaki2024hackphyr}, CPSForge targets CPS process-level attacks rather than IT-infrastructure exploitation. Table~\ref{tab:comparison} summarizes these differences across seven capabilities; no prior work in our survey covers all seven.

\subsection{Extended Threat Tiers: Preliminary Capability}
\label{sec:discussion:tiers}

Beyond the 333 Tier~1 (I/O MitM) runs reported in Section~\ref{sec:eval}, we conducted preliminary capability assessments of the two extended threat tiers introduced in Section~\ref{sec:threat:tiers}.

\textbf{Tier~3: Logic Code Generation.} The LogicAnalyzer scanned SCL source code for all three evaluation scenes using the same Qwen2.5-3B-Instruct model (4-bit NF4). The vulnerability scanner identified 5~vulnerabilities across three scenes---2~high-severity on Level Control (\texttt{SetpointIn}, \texttt{Enable}), 3~low-severity on Sorting by Weight (\texttt{MeasuredWeight}, \texttt{iState}, \texttt{Enable})---while Sorting by Height yielded 0 due to JSON truncation on the 15\,KB SCL input (exceeding the 3B model's reliable output length). Despite the scanner limitation, the modification generator produced 7~adversarial code modifications per scene (21 total) across seven attack categories (dead code injection, comparison inversion, timer alteration, interlock removal, gradual drift, state shortcut, sensor clamping). \textbf{Parse success rate: 21/21 (100\%)} across all three scenes, with 5~first-attempt JSON parse failures recovered via retry. LLM latency ranged from 21--45\,s per modification on smaller scenes (8--9\,KB SCL) to 34--261\,s on the largest scene (15\,KB SCL), totaling 1524\,s (25.4\,min) for the full analysis. The most stealthy modifications---sensor clamping (replacing a live sensor read with a constant, e.g., \texttt{IsTall := TRUE}) and interlock removal---received detection difficulty scores of 0.9 (model self-assessment), while dead code injection (adding visible new branches) scored 0.5.

To validate that LLM-generated modifications produce real physical effects, we deployed one modification per scene to the live S7-1200 PLC. All three used \emph{comparison inversion}---the highest-stealth category (minimal code change, no structural additions). The end-to-end pipeline proceeds as follows: the LLM generates an adversarial SCL modification ($\sim$33--36\,s), a 5-tier code matching algorithm localizes the change in the original source, TIA Portal compiles the modified program (\textbf{0 compile errors} on all three scenes), and the modified program is downloaded to the PLC. Observation runs (60~steps, 500\,ms polling) then measure tag deviations against a baseline captured under the original program.

\textbf{Results:} On Level Control, inverting the PID error comparison (\texttt{>}~$\rightarrow$~\texttt{<}) caused the fill valve to remain at 0\%, producing 100\% deviation on the key actuator tag. On Sorting by Height, inverting the classification condition (\texttt{IF IsTall}~$\rightarrow$~\texttt{IF NOT IsTall}) jammed the sorting system entirely: 11~tags exceeded 20\% deviation (up to 900\% on \texttt{high\_sensor}). On Sorting by Weight, inverting a threshold comparison (\texttt{<}~$\rightarrow$~\texttt{>=}) caused complete misclassification: 11~tags exceeded 20\% deviation (up to 2350\% on \texttt{send\_left}). In all three cases, a \emph{single-character code change} generated by a 3B-parameter model compiled without errors and caused maximum physical disruption---validating the Stuxnet OB1/OB35 threat model with an autonomous LLM agent.

\textbf{Tier~2: Deep State Manipulation.} Two pilot runs on Level Control confirmed that writes to \texttt{Enable} (BOOL) persist indefinitely---the PLC reads but never re-initializes this variable, so a single S7 write disables the entire process without requiring continuous injection. This validates the Tier~2 threat model: internal state variables that the PLC trusts implicitly are more dangerous than I/O tags that the controller overwrites each scan cycle. A full Tier~2 experiment matrix (180~cells: 2~models $\times$ 2~contexts $\times$ 5~defenses $\times$ 3~scenes $\times$ 3~repeats) is designed and ready to execute.

\subsection{Future Directions}

Several extensions are planned. First, \emph{reducing LLM defender FPR}: the measured 95--100\% FPR demonstrates that prompt engineering and fine-tuning alone are insufficient for write-level discrimination; future work should explore few-shot exemplars of legitimate writes in the defender prompt, contrastive fine-tuning with explicit allow/block pairs on the same tag values, and hybrid architectures where a lightweight statistical model pre-filters obvious legitimate writes before invoking the LLM on ambiguous cases. Second, expanding the frontier model comparison to additional API models (GPT-4, Claude) and mid-range open models (7B--13B) to characterize the full capability--scale curve---RQ6 shows that frontier models eliminate self-deterrence and achieve dramatically higher ASR on some scenes, but the transition point between ``self-deterring'' and ``non-self-deterring'' model scales is unknown. Third, expanding to additional Factory~I/O scenes, more complex PLC programs, and cross-PLC evaluation (e.g., Allen-Bradley, Schneider). Fourth, executing the full Tier~2 experiment matrix to quantify deep-state attack effectiveness and validate the StateConsistencyChecker defense. Fifth, integrating LLM-assisted invariant synthesis to automatically derive scene-specific detector rules from PLC documentation or runtime traces.
