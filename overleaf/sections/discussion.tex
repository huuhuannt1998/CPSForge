\section{Discussion}
\label{sec:discussion}

\subsection{Why Real PLC Execution Matters}

A central design choice in CPSForge is the use of a real Siemens S7 PLC rather than a purely synthetic or mock controller. This choice increases implementation complexity but strengthens evaluation realism. Real controller scan timing, actual tag behaviour, and live interaction with Factory~I/O provide a more faithful substrate for studying both attack validity and defence response than purely software-based simulation. For a framework focused on LLM use in CPS security, this realism is important because it reduces the risk that observed results are artefacts of an oversimplified backend. Prior PLC-based testbeds~\cite{dehlaghi2023icssim, garcia2025sphere, pramadi2026simpleics} establish this principle; CPSForge extends it to LLM-driven experimentation. We note that Factory~I/O is a software process emulator, not a physical plant; Section~\ref{sec:background} discusses the implications of this PLC-in-the-loop configuration.

\subsection{Why the LLM Is Constrained}

CPSForge intentionally avoids treating the LLM as a trusted autonomous controller. This is both a safety decision and a research decision. From a safety perspective, unrestricted direct actuation is inappropriate in a live CPS setting~\cite{lanotte2022runtime_ics, baird2024scalable_enforcement}. From a research perspective, a structured and mediated interface makes it possible to evaluate the LLM's reasoning quality without conflating model output quality with uncontrolled execution privilege. The framework therefore studies what the LLM can contribute under explicit process and safety constraints.

\subsection{Observed Strengths}

The evaluation provides several observations. First, the PLC-in-the-loop environment produces measurable process impact: across 96~experiment runs (68~eval-flagged) totalling 11{,}864~time-series steps, all shield-approved scripted and random actions executed successfully on the live Siemens S7-1200, with Level Control showing the highest exploitability (scripted ASR~=~0.75, random ASR~=~0.75). Second, the LLM batch attacker generated process-valid attacks across all five scenes, confirming that structured prompting with JSON schema validation can reliably translate LLM reasoning into concrete PLC operations. Third, the campaign attacker's stealth score of 1.0 on Level Control exposed a coverage gap in rule-based detectors---gradually-escalating perturbations that remain within threshold bounds are invisible to fixed-threshold monitors. Fourth, the safety shield mediated all writes across all configurations, rejecting out-of-range perturbations (20--30\% on sorting scenes) and strict-invariant violations (84\% in Level Control agent mode), while permitting no unsafe execution. Fifth, when the campaign exposed detector coverage gaps on Level Control, hard-case retraining produced a single-round F1 recovery from 0.00 to 0.92; while this does not yet demonstrate generalisation to novel attack sequences, it provides preliminary evidence that the adaptation mechanism can address specific detector blind spots. Sixth, framework overhead is negligible: the middleware's per-step processing averages 1.9\,ms (median 0.3\,ms), consuming less than 0.4\% of the 500\,ms polling interval, and the benign false-positive rate across 87~detector--trace evaluations is 0.0001.

The multi-agent architecture successfully demonstrated concurrent attacker and defender agent operation through the full PLC loop, with independent LLM inference, shield validation, and PLC I/O. The infrastructure supports the closed-loop workflow even when the underlying LLM model is the performance bottleneck.

\subsection{Limitations}

The current evaluation has several limitations.

\textbf{Agent-mode model capacity.} Initial agent-mode experiments with Phi-3-Mini-4K-Instruct (3.8B parameters) achieved only 1.6--2.1\% schema compliance, producing valid structured actions in 1 out of 47--61 attacker cycles per scene. Switching to Qwen2-7B-Instruct (7B parameters) raised schema compliance and shield approval rates to 95--98\% across four of five scenes, with zero attacker errors. Level Control remains the exception (12\% approval) due to strict process invariants rather than schema failures. These results bracket the minimum model capacity for effective CPS agent operation: 3.8B models are insufficient, while 7B models with instruction-tuned JSON output are adequate for structured CPS reasoning across most scenes.

\textbf{LLM attacker effectiveness relative to baselines.} A natural question is whether the LLM attacker provides value beyond random perturbation. In the current evaluation, the LLM batch attacker outperforms random on Sorting by Weight (ASR~0.67 vs.~0.29) and From A to B (0.50 vs.~0.23), but underperforms on Level Control (0.33 vs.~0.75) and achieves zero ASR on Filling Tank and Sorting by Height where random achieves non-zero impact. The LLM generates fewer actions per run (1--3 vs.~10 for random), so a per-action comparison would be more favourable; however, the current experimental design does not control for action count. We therefore do not claim that the LLM attacker is uniformly superior to random; rather, the LLM's value lies in (a)~its ability to target process-critical parameters (as on Sorting by Weight), (b)~the campaign planner's capacity for multi-phase evasion, and (c)~the structured schema that integrates LLM reasoning into an automated pipeline. Future work should include controlled comparisons with equal action budgets.

\textbf{Detector precision.} Detector precision ranged from 0.02 to 0.87 across configurations, with false positive counts of 13--164 per run. The threshold detector fires conservatively on any state deviation, producing many false alarms during normal process variation. This underscores the need for adaptive threshold calibration~\cite{moriano2025adaptive_anomaly} and learned anomaly scoring to reduce false positive rates to operationally acceptable levels.

\textbf{Sorting scene resilience.} Sorting by Height showed low attacker effectiveness (scripted ASR~=~0.12, random ASR~=~0.06, LLM batch ASR~=~0.00), reflecting discrete-control scenes' inherent resilience to single-tag perturbations. Each item follows an independent control path, making single-tag overrides less likely to corrupt overall throughput. More sophisticated multi-step or multi-tag attack strategies, potentially with hierarchical LLM planning, are needed to effectively attack complex discrete scenes.

\textbf{Constrained action space.} Attacks are bounded by the configured attack surface, duration caps, and cooldown windows enforced by the shield. While essential for safety, this limits the attacker's ability to sustain long-duration perturbations or target arbitrary tags. Future work should explore graduated relaxation of these constraints in controlled settings.

\textbf{Scene scale and representativeness.} The evaluated scenes range from 4 to 35~tags, which is smaller than full-scale ICS testbeds such as SWaT (51~sensors/actuators across 6~linked process stages)~\cite{mathur2016swat} or real industrial plants with hundreds to thousands of tags. The Factory~I/O scenes are educational-grade demonstrations that cover diverse control paradigms (continuous, discrete, threshold-based) but lack the cross-subsystem dependencies, cascading failure modes, and complex interlock logic found in production environments. Whether the attack effectiveness patterns observed here---particularly the LLM's advantage on threshold-parameter scenes---generalise to higher-complexity plants remains an open question.

\textbf{Single LLM per mode.} Both batch-mode and agent-mode evaluations use Qwen2-7B-Instruct. Comparing across multiple LLM backends---including larger open-source models and API-served models---would strengthen generalisability claims and disentangle model capability from framework capability.

\textbf{Statistical power.} Of the 17 (scene, attacker) pairs, only 8 have $n \geq 2$ independent runs. Confidence intervals for pairs with $n = 2$ are wide (e.g., From A to B scripted ASR: 0.27 [0.00, 0.72]), reflecting the inherent stochasticity of LLM-driven attacks against a live PLC process. Increasing the number of repeated trials per configuration---particularly for LLM batch and campaign modes---is needed before individual per-cell metrics can be considered stable.

\textbf{Adaptation dynamics.} The Level Control adaptation result (F1: 0.00$\to$0.92 after one retraining cycle) represents a single dramatic recovery from complete evasion rather than gradual refinement over multiple rounds. This demonstrates that hard-case retraining can be highly effective when the detector has a clear coverage gap, but does not yet demonstrate incremental improvement over many rounds of diverse attacks. On Sorting by Weight, the observed F1 improvement (0.65$\to$0.92) occurred without any detector retraining, suggesting that the metric change reflects variability in the LLM campaign planner's attack choices across rounds rather than genuine adaptation. Future work should isolate adaptation effects from LLM stochasticity using fixed attack sequences.

\textbf{Single PLC and plant.} All experiments use one Siemens S7-1200 PLC with Factory~I/O. While the scene abstraction supports diverse plant configurations, generalisability to other PLC families (e.g., Allen-Bradley, Schneider) or real physical plants remains to be validated.

\textbf{ML detector portability.} Trained ML detectors (OCSVM, Isolation Forest, LSTM-AD) are sensitive to the feature dimensionality of the scene on which they were trained. When evaluated on traces from a different scene configuration with a mismatched tag count, pre-trained models fail. This motivates per-scene model management and automated retraining when scene configurations change.

\textbf{Ground-truth labelling.} As discussed in Section~\ref{sec:methodology:gt}, protocol-based attack labels do not perfectly correspond to physical-process anomalies. Steps where the injected value causes no observable deviation are still labelled ``attack-active,'' and residual effects after an attack ends are labelled ``normal.'' This means the reported F1 values are approximate and would differ under a physics-based labelling scheme. Developing dual-label ground truth---protocol-level and physics-level---is an important direction for future work.

\subsection{Comparison to Most Related Work}

Compared to AttackLLM~\cite{ahmed2025attackllm}, CPSForge operates in a live PLC loop rather than offline, includes a safety shield and defender stack, and supports closed-loop adaptation. Compared to Evo-Defender~\cite{hu2025evodefender}, CPSForge uses LLM reasoning rather than fuzzing for attack generation and runs on a real PLC rather than a simulator. Compared to PentestGPT~\cite{deng2024pentestgpt} and Hackphyr~\cite{rigaki2024hackphyr}, CPSForge targets CPS process-level attacks rather than IT-infrastructure exploitation. \subsection{Future Directions}

Several extensions are planned. First, evaluating larger LLM backends (13B+ open-source, GPT-4, Claude) to assess the influence of model capacity on attack quality and defence reasoning---our results show that 7B models are sufficient for reliable structured CPS agent operation in most scenes. Second, extending the campaign attacker to longer multi-round campaigns with persistent state across sessions and adversarial adaptation to observed detector behaviour. Third, reducing detector false positives through adaptive threshold calibration, learned anomaly scoring, and the adaptation loop with accumulated hard-case traces---our campaign experiments show that adaptation is most effective when detectors have coverage gaps, but the current retraining uses Isolation Forest only; integrating LSTM-AD and ensemble retraining could yield further gains. Fourth, expanding to additional Factory~I/O scenes and more complex PLC programs. Fifth, integrating LLM-assisted invariant synthesis to automatically derive scene-specific detector rules from PLC documentation or runtime traces.
